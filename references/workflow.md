# 执行流程（Workflow）

本文档是 birthday-reminder-gift 的执行核心，按触发场景分三节。执行前先判断当前属于哪个场景。

---

## §1 初始化（新使用者建档）

适用：使用者第一次使用本技能，或更换设备/环境。

### 步骤

1. **获取画像数据**
   - 使用者提供人物清单（姓名、农历生日、性别、关系分类、爱好等）；信息不全时逐项补齐，**禁止编造**生日、年龄或爱好。
   - 打开 `assets/profile-template.json`，按 `references/data-schema.md` 字段说明填入；或用问答方式收集后由 AI 代为生成 JSON。
2. **校验数据并预填当年生日**
   - 用 `scripts/lunar_conversion.py` 或万年历验证每个农历生日可换算；闰月生日须确认 `lunar_leap_month`。
   - 用 `zodiac_sign` 推算规则生成星座（见 data-schema.md），写入画像。
   - **立即换算当年公历生日**：用当年农历年 + `lunar_birthday` → 当年公历日期，写入 `annual_birthday[当年]`；计算当年 `age`。这一步必须在初始化当天完成，否则第一次月度扫描读不到当年数据。
3. **确定数据文件路径**
   - 默认建议 `birthday_profiles.json` 放在使用者项目目录；与使用者确认后作为固定路径，后续所有任务读取该路径。
4. **配置推送通道**
   - 确认双通道开关：飞书消息（默认开）与邮箱（默认开）。
   - 邮箱：确认收件邮箱地址（可由使用者提供，或默认使用 Agent Mail 绑定的发件账户自身）；发件账户由 Agent Mail 自动使用已绑定别名，无需额外配置。
   - 记录通道配置（可写入画像文件顶层 `notify` 字段或单独说明），后续提醒任务按此推送。
5. **建立月度扫描任务（唯一定时任务）**
   - 先读 doubao-cron-scheduler 技能，创建**每月 1 日 10:30** 触发的任务（cron 表达式 `30 10 1 * *`）。
   - 任务 query 写明：读取画像文件路径 → 若当天是 1 月 1 日先执行 §2 开年流程 → 执行 §3 月度扫描流程 → 推送命中的生日提醒。
   - 任务标题：「生日月度扫描」。
   - 初始化当天若未来 60 天内已有人生日，可立即手动触发一次 §3 补跑，不必等到下个月 1 号。
6. **回执**
   - 向使用者输出：画像条数、数据文件路径、月度扫描任务已建立、下次触发时间。

---

## §2 开年流程（仅 1 月 1 日触发时执行）

适用：每月 1 日任务到点执行后，判断**当天是 1 月 1 日**，先执行本节；其他月份跳过本节直接进 §3。

### 步骤

1. **读取画像**：读取固定路径的画像 JSON，校验 schema（缺失/非法字段见 data-schema.md 错误处理）。
2. **逐人换算**（对每条记录）：
   - 农历换算：当年农历年 + `lunar_birthday` → 当年公历日期，写入 `annual_birthday[当年] = {date, weekday}`；`weekday` 用 date 算出中文星期（周一~周日）；闰月按 `lunar_leap_month` 处理（见 lunar-conversion.md）。
   - 更新年龄：`age = 当年年份 - birth_year`；当年公历生日已过则已满该岁，未过则未满（展示时说明即可）。
   - 星座：**已存在则跳过，绝不重算**（星座终身不变，用出生年公历月日查得）；仅当 `zodiac_sign` 为空时，用 `birth_year` 那年的农历生日换算出的公历月日补全。
3. **重置去重标记**：将所有人的 `gift_reminded_year` 清空（新一年重新去重）。
4. **写回画像**：将更新后的 `annual_birthday`、`age`、`zodiac_sign` 保存回 JSON（写前备份 `.bak`）。
5. **输出全年清单回执**：表格列出每人 → 当年公历生日 → 预计首次被本月扫描命中的月份，供使用者核对查漏。

---

## §3 月度扫描流程（每月 1 日均执行）

适用：每月 1 日 10:30 任务到点执行。一个任务覆盖全量画像，不再为单人建子任务。

### 步骤

0. **判断是否先跑开年**：若当天是 1 月 1 日，先完整执行 §2，再继续本节。

1. **读取全量画像**：读取固定路径的画像 JSON，校验 schema。
2. **计算每个人距今天数**：
   - 对每条记录，取 `annual_birthday[当年].date`（当年公历生日），计算"今天 → 该公历生日"的天数差 `days_left`；`weekday` 字段用于推送时展示（如"周六生日"）。
   - 若当年公历生日已过（`days_left < 0`），跳过此人（今年已过完）。
3. **筛选命中者**：
   - 筛选条件：`0 ≤ days_left ≤ 60` 且 `gift_reminded_year != 当年年份`（今年还没推过）。
   - 按 `days_left` 升序排列。
   - 若无人命中，静默退出，不推送、不打扰使用者。
4. **对每个命中者执行提醒**：
   - **距离分档**：
     - `days_left = 0`：今天生日！紧急高亮，侧重行动提示（发祝福/打电话）。
     - `1 ≤ days_left ≤ 15`：本阶段生日，行动提醒 + 礼物建议。
     - `16 ≤ days_left ≤ 60`：提前预告，礼物建议慢慢看。
   - **双层礼物检索**（`days_left ≤ 30` 时执行；`> 30` 可给简版建议）：按 `references/gift-search.md` 执行小红书种草 → 通用搜索 → 人物代入推演，输出 5 个备选礼物。
   - **推送（双通道）**：
     - 飞书消息：用 `lark-cli im +messages-send --chat-id <notify.feishu_chat_id> --markdown "<内容>"` 发送。**标题加粗**：人名/日期/每个礼物名都用 `**` 包裹（如 `**🎂 生日提醒：小红**`、`**1. 富士 mini12**`）。消息精简（5个备选一行一个），详细评测走邮件。语气按关系分类调整（伴侣重心意、家人重实用、朋友重新奇）。
     - 邮箱：经 Agent Mail 代发到配置地址，`body_format=HTML`。**标题用 `<h3><b>` 或 `<b>` 加粗加大**，正文含完整礼物清单（含优缺点/避坑/价格/平台/来源）。
     - 任一通道不可用时保留另一通道并告知，不静默跳过。
   - **去重标记**：推送成功后，将此人 `gift_reminded_year` 设为当年年份，写回画像 JSON（下次扫描跳过）。
5. **回执**：输出本次扫描命中人数、命中者清单、各通道推送结果。无人命中时回执简略带过即可。

   **Agent Mail 授权过期处理**：
   - 发送失败且错误为授权过期/未授权时：邮件通道标记为「需重新授权」，不反复重试；飞书通道照常推送。
   - 通知使用者重新授权 Agent Mail；恢复后自动可用。

## ReAct 执行纪律（强制，不可跳过）

本技能所有流程（§1 初始化、§2 开年、§3 月度扫描）必须走 **思考 → 行动 → 观察** 循环，禁止一口气跑完不回头核对。每完成一个动作，必须停下来观察结果并对照下方检测基准；任何一项不通过，立即停下、报错、告知使用者，禁止蒙混推进。

### 检测基准（Pre-flight Checklist）

每次任务触发后，按顺序逐项核对：

**检查点 1：画像文件可读**
- 动作：`Read` 画像 JSON 文件。
- 通过条件：JSON 能正常解析；`people` 数组存在且非空；`updated_at` 字段存在。
- 不通过处理：停止流程，告知使用者"画像文件损坏或为空"，从 `.bak` 恢复或让使用者重建。

**检查点 2：当年数据完整**
- 动作：遍历 `people`，检查每个人是否有 `annual_birthday[当年]`。
- 通过条件：`annual_birthday[当年]` 是对象，含 `date`（格式 `YYYY-MM-DD`）和 `weekday`（周X）；`age` 字段存在；`zodiac_sign` 非空。
- 不通过处理：`annual_birthday[当年]` 或 `age` 缺失者用 `scripts/lunar_conversion.py` 重新换算并补全（含 weekday）；`zodiac_sign` 仅在为空时用 `birth_year` 那年的农历公历月日补全——**已存在的星座字段绝不重算、不覆盖**（星座终身不变）。

**检查点 3：days_left 计算可复现**
- 动作：对每个人用"当年公历生日 − 今天"算出 `days_left`。
- 通过条件：
  - `days_left < 0` → 标记"今年已过"，跳过。
  - `0 ≤ days_left ≤ 60` → 进入候选池。
  - `days_left > 60` → 跳过。
- 不通过处理：日期格式非法或算出来是负数但月份明显不对（如1月生日算成-300天），说明 `annual_birthday[当年]` 写错年份，回到检查点2。

**检查点 4：去重标记正确**
- 动作：对候选池中的人，检查 `gift_reminded_year`。
- 通过条件：`gift_reminded_year == 当年` 的人必须排除；缺失或为旧年份的保留。
- 不通过处理：若发现某人今年明明推过但标记为空（上次推送写回失败），告知使用者"可能重复推送"，由使用者决定是否跳过，不自动静默处理。

**检查点 5：推送通道与写回**
- 动作：推送前确认双通道开关；推送后立即写回 `gift_reminded_year`。
- 通过条件：
  - 飞书推送成功或明确告知失败原因；
  - 邮箱推送成功或标记"需重新授权"；
  - **至少一个通道成功**才允许写 `gift_reminded_year`（两个都失败不打标记，下次重推）；
  - 写 JSON 前先复制 `.bak`。
- 不通过处理：写回失败时，本次推送结果不丢弃，在回执中明确列出"已推送但标记未写回"，下次扫描人工核对。

**检查点 6：礼物推荐必须有真实检索证据（禁止凭记忆推荐）**
- 动作：对每个命中者的礼物清单，逐条核对是否来自真实外部检索。
- 通过条件：每个备选必须包含以下5项，缺一不可：
  1. **真实优缺点**：至少2个👍优点 + 2个👎缺点，来自真实用户测评，不是"颜值高/性价比好"这种空话；
  2. **避坑建议**：明确指出常见踩雷点（如"中样别当正装买""银镀铑会氧化""相纸8元/张"）；
  3. **最优惠价格**：具体数字区间，不是"约几百元"；
  4. **最优惠平台**：具体到淘宝/天猫/京东/抖音/识货比价等，并说明该渠道是否官方店/百亿补贴/旗舰店；
  5. **来源链接**：至少1条可溯源的评测或比价来源。
- 不通过处理：任何一项缺失，**禁止推送**；回去用 `general_search` 或浏览器检索补全后再推。凭模型记忆"我觉得这款不错"直接触发此条，必须重做检索。
- 反模式：禁止只写"很适合她""颜值高""性价比好"；禁止不给价格区间；禁止不给购买平台。

### 反模式（禁止）

- 禁止：读完 JSON 不核对字段直接算 days_left。
- 禁止：某人没在画像里就凭名字脑补生日/爱好。
- 禁止：双通道都失败还写 `gift_reminded_year`（会导致此人今年再也收不到提醒）。
- 禁止：写完 JSON 不验证文件是否真的保存成功。
- 禁止：把模型记忆的"今天日期"当锚点，日期必须来自系统或 `get_current_time`。

---

## 通用纪律

- 画像文件写入前先备份旧文件（`birthday_profiles.json.bak`）。
- 任何人名、生日、爱好都来自画像文件，禁止在流程中编造或脑补。
- 定时任务创建/更新前先读 doubao-cron-scheduler 技能；任务 ID 不展示给使用者。
- 所有日期锚点（"今天""当年"）必须来自系统时间，禁止凭模型记忆。
